# Databases and migrations

Every environment has **one PostgreSQL database**, `dafne`, split into
**schemas** with fixed names. Tables are defined with
[Drizzle](https://orm.drizzle.team); migrations are generated by
drizzle-kit.

## One schema per app

| Schema   | Owner                                         | What                                                  |
| -------- | --------------------------------------------- | ----------------------------------------------------- |
| `auth`   | `@dafne/backend-database-auth` (`apps/auth`)  | Users, sessions, accounts, verification, `app_access` |
| `sales`  | `@dafne/backend-database` (`apps/sales-api`)  | The sales app's tables                                |
| `<app>`  | the app's schema package                      | One per new app                                       |
| `core`   | its own package (not created yet)             | Tables shared by several apps                         |
| `changelog` | `@dafne/backend-database-changelog`        | The change log of the CRUD resources ([below](#the-change-log)) |

Rules:

- **A table is born in the schema of the app that creates it.** It moves
  to `core` when another app must read it or reference it, with
  `ALTER TABLE sales.<table> SET SCHEMA core` (rows, indexes and foreign
  keys move with it, no copy). The CLI support for this is planned (see
  [ROADMAP.md](../ROADMAP.md)).
- **Dependencies go one way: app → core → auth**, foreign keys included.
  E.g. `sales.customer.created_by_id` points to `auth.user`.
- **Core data is written only by its feature lib** (e.g.
  `@dafne/backend-customers`), and core migrations live in the core
  package, never in an app.
- `public` holds only the migrator's history (`public._migrations`).

## Schema packages

A schema belongs to a **package**, not to an app: a shared schema may be
used by several apps. A schema package:

- declares its schema in `package.json`: `"dafne": { "schema": "sales" }`;
- declares its tables in it, with Drizzle: `salesSchema.table(...)`
  (`pgSchema('sales')`, in `src/tables/sales.ts`), so every query names the
  schema (`"sales"."customer"`);
- has a `drizzle.config.ts` (`dialect: 'postgresql'`, `schemaFilter` set to
  its schema) and keeps its migrations in `migrations/` (one folder per
  migration).

`@dafne/backend-database` exports `DatabaseModule` (global, connects to
`DATABASE_URL` with node-postgres) and `schema.ts`, built from
`src/tables/*.ts`. Inject it with
`@InjectDrizzle() private readonly db: Database`. It doesn't migrate.

### Tables of other schemas (`auth`)

The auth tables are in `pgSchema('auth')` too, so the sales tables point
to `auth.user` with plain `.references(() => user.id)`, and drizzle-kit
writes the foreign key with the schema (`REFERENCES "auth"."user"("id")`).

drizzle-kit writes **every table its schema files export** into the
package's migrations, `schemaFilter` notwithstanding. So the sales package
re-exports `user` from `src/auth.ts`, outside `src/tables/` (the folder
drizzle-kit reads): the sales migrations never create `auth.user`.

Better Auth's tables (`src/better-auth.ts` of `@dafne/backend-database-auth`)
are written by its CLI, then moved into the auth schema
(`pgTable` → `authDb.table`, timestamps with time zone) by
`tables:schema`. Both run with
`pnpm --filter @dafne/backend-auth auth:schema:generate`.

### Column types

- Ids are `serial('id').primaryKey()` (an `integer` with a sequence),
  unless the resource was generated with `--id-type uuid`
  (`uuid('id').primaryKey().defaultRandom()`, a key to it is `uuid`, the
  route uses `UuidPipe`, a key in a body `requiredUuid` / `optionalUuid`) or `--id-type varchar` (random by `$defaultFn`, a
  key to it is a `varchar` of the same length, the route uses
  `new TextIdPipe(<length>)`).
  The database picks them (`insert(…).values(…).returning({ id })`), and a
  key to another table is `integer('<name>_id')`. The exceptions: the
  tables of the `auth` schema (Better Auth's text ids, and `app_access`),
  so the `created_by_id` / `updated_by_id` keys to `auth.user` are text,
  and `country`, whose key is its ISO 3166-1 code.
- In the API an id is a number: `@Param('id', IdPipe) id: number`
  (`@dafne/backend-common`, a 404 for anything that isn't a positive
  integer), `requiredId` / `optionalId` (`@dafne/contracts`) for a key in a
  body, which a form sends as text.
- Timestamps are `timestamp(..., { precision: 3, withTimezone: true })`
  (`timestamptz`): stored in UTC, whatever the server's time zone.
- Enums are `text('x', { enum: [...] })`: typed in TypeScript, plain `text`
  in the database (adding a value needs no migration step).
- Text filters use `ilike` (Postgres' `like` is case sensitive).
- Updates check `result.rowCount`; constraint errors carry their SQLSTATE
  (`23505` unique, `23503` foreign key) and the constraint's name.

## The migrator

`@dafne/backend-migrator` applies the migrations of **every** schema
package in **one order, by timestamp**, whatever their schema. A fresh
database replays the history as it happened (e.g. a table created in
`sales`, later moved to `core`).

- Each migration runs **in a transaction**, with `search_path` set to its
  schema, and is recorded in `public._migrations` in the same
  transaction: a failing migration leaves nothing behind.
- A schema's first migration creates it (drizzle-kit writes
  `CREATE SCHEMA`).
- One run at a time (`pg_advisory_lock`).
- It needs **`MIGRATIONS_DATABASE_URL`**: the database URL, with the user
  that owns it (and so creates and alters its schemas). Set it in the
  environment or in `packages/backend/migrator/.env`.

## Creating the database

```sh
pnpm dafne db create
```

creates the database and its owner named by `MIGRATIONS_DATABASE_URL`
(`postgres://dafne:secret@host:5432/dafne`: role `dafne`, password
`secret`, database `dafne`), connected as the superuser of
`ADMIN_DATABASE_URL`. The database is `UTF8` with ICU collation (`und`:
names sort as people expect, `acme`, `Àlfa`, `Zeta`; and unlike libc it
doesn't change with the OS's glibc). Running it again changes nothing.
In production the operator may create them by hand instead:

```sql
CREATE ROLE dafne LOGIN PASSWORD '…';
CREATE DATABASE dafne OWNER dafne TEMPLATE template0 ENCODING 'UTF8'
  LOCALE_PROVIDER icu ICU_LOCALE 'und' LOCALE 'C.UTF-8';
```

```sh
pnpm dafne db migrate                     # apply the pending migrations
pnpm dafne db generate                    # a migration of the sales schema from the table changes
pnpm dafne db generate <package> --name x # of another schema package
pnpm dafne db generate --custom --name x  # empty, for SQL written by hand
```

`generate` runs drizzle-kit as it is: no patch and no fixes afterwards.

In development, `dafne dev` runs `migrate:dev` before the APIs; it skips
with a warning when `MIGRATIONS_DATABASE_URL` isn't set.

## The change log

`changelog.change` records the changes of the CRUD resources that turn it
on (`ChangelogModule.forFeature`, in `@dafne/backend-changelog`; see
[Architecture](architecture.md#change-log)): one row per create, update,
delete or status change, with the fields that changed (`changes`, jsonb:
`{ "notes": { "from": "a", "to": "b" } }`), who made it (`actor_id` →
`auth.user`) and when. It is written in the transaction of the write.
Only `@dafne/backend-changelog` writes it. It depends only on `auth`, so
any app can log to it.

The table is **partitioned by resource** (`PARTITION BY LIST (resource)`),
so it can grow without one huge index:

- `change_default` (DEFAULT) takes every resource without a partition of
  its own, so **a new resource needs no migration**;
- `change_sales_orders` takes `sales-orders`.

drizzle-kit can't create partitioned tables, so the package's
`src/change.ts` defines the table for queries only (drizzle-kit doesn't
see it), and its migrations are written by hand:
`pnpm dafne db generate @dafne/backend-database-changelog --custom --name <name>`.

**A resource of its own partition.** `dafne g backend-changelog
<resource> --partition` (or `dafne g backend-resource <name> --changelog
--partition`) writes the migration below, the right one of the two: the
CLI asks for it when the flag is left out. By hand: if the resource has no rows yet
(e.g. in the migration that comes with its first `forFeature`), it's one
statement:

```sql
CREATE TABLE "changelog"."change_invoices" PARTITION OF "changelog"."change" FOR VALUES IN ('invoices');
```

If `change_default` already holds its rows, Postgres refuses that. Move
them in the same migration (it runs in a transaction, and locks the table
while it runs):

```sql
ALTER TABLE "changelog"."change" DETACH PARTITION "changelog"."change_default";
--> statement-breakpoint
CREATE TABLE "changelog"."change_invoices" PARTITION OF "changelog"."change" FOR VALUES IN ('invoices');
--> statement-breakpoint
INSERT INTO "changelog"."change" SELECT * FROM "changelog"."change_default" WHERE "resource" = 'invoices';
--> statement-breakpoint
DELETE FROM "changelog"."change_default" WHERE "resource" = 'invoices';
--> statement-breakpoint
ALTER TABLE "changelog"."change" ATTACH PARTITION "changelog"."change_default" DEFAULT;
```

## Migrations in production

Two options:

1. **The apps migrate on startup** with `MIGRATE_ON_START=true` (and
   `MIGRATIONS_DATABASE_URL`). `main.ts` calls `migrateOnStart` before Nest
   starts. Every app's build carries the migrations of **every** schema
   (`dist/migrations/<schema>/`), since they run in one order. Apps or
   replicas starting together are safe: one takes the lock, the others wait
   and find nothing to apply. A failing migration stops the app.
2. **A deploy step** runs `pnpm nx run @dafne/backend-migrator:migrate`
   before the apps are updated, and `MIGRATE_ON_START` stays off. Use this
   when the apps shouldn't hold a user with DDL rights.

Either way, a migration must keep working with the apps still running: add
first, drop in a later release.

## Roles and grants

Each app connects to `dafne` with its own role (`DATABASE_URL`), with
rights on its schema only, plus what it points to elsewhere. E.g. for the
sales API:

```sql
GRANT USAGE ON SCHEMA sales TO dafne_sales;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA sales TO dafne_sales;
ALTER DEFAULT PRIVILEGES FOR ROLE dafne IN SCHEMA sales
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO dafne_sales;
GRANT USAGE ON SCHEMA auth TO dafne_sales;
GRANT SELECT, REFERENCES ON auth."user" TO dafne_sales;
-- The change log: write and read, never change.
GRANT USAGE ON SCHEMA changelog TO dafne_sales;
GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA changelog TO dafne_sales;
GRANT USAGE ON SEQUENCE changelog.change_id_seq TO dafne_sales;
```

(`dafne` being the role of `MIGRATIONS_DATABASE_URL`, which owns the
tables.) The operator sets them up.
