# Databases and migrations

All databases live on **one MySQL server** per environment, with fixed
names. Tables are defined with [Drizzle](https://orm.drizzle.team);
migrations are generated by drizzle-kit.

## One database per app

| Database      | Owner                                       | What                                             |
| ------------- | ------------------------------------------- | ------------------------------------------------ |
| `dafne_auth`  | `@dafne/backend-database-auth` (`apps/auth`) | Users, sessions, accounts, verification, `app_access` |
| `dafne_sales` | `@dafne/backend-database` (`apps/sales-api`) | The sales app's tables                           |
| `dafne_<app>` | the app's database package                  | One per new app                                  |
| `dafne_core`  | its own package (not created yet)           | Tables shared by several apps                    |

Rules:

- **A table is born in the database of the app that creates it.** It moves
  to `dafne_core` when another app must read it or reference it, with
  `RENAME TABLE` (same server: rows, indexes and foreign keys move with it,
  no copy). The CLI support for this is planned (see
  [ROADMAP.md](../ROADMAP.md)).
- **Dependencies go one way: app → core → auth**, foreign keys included.
  E.g. `dafne_sales.customer.createdById` points to `dafne_auth.user`.
- **Core data is written only by its feature lib** (e.g.
  `@dafne/backend-customers`), and core migrations live in the core
  package, never in an app.

## Database packages

A database belongs to a **package**, not to an app: a shared database may be
used by several apps. A database package:

- declares its database in `package.json`:
  `"dafne": { "database": "dafne_sales" }`;
- has its Drizzle tables in `src/` and a `drizzle.config.ts`;
- keeps its migrations in `migrations/` (one folder per migration).

`@dafne/backend-database` exports `DatabaseModule` (global, connects to
`DATABASE_URL`) and `schema.ts`, built from `src/tables/*.ts`. Inject it with
`@InjectDrizzle() private readonly db: Database`. It doesn't migrate.

### Tables of other databases (`dafne_auth`)

`dafne_auth`'s tables are defined in `mysqlSchema('dafne_auth')`, so every
query names the database (`dafne_auth`.`user`). That lets apps connected to
their own database point to users with foreign keys and join them. Since
drizzle-kit ignores tables in a `mysqlSchema`, they're written twice from
one source: `src/kit/*.ts` (plain tables, for drizzle-kit) and the qualified
ones, generated by `pnpm --filter @dafne/backend-database-auth
tables:qualify` (a test fails when they're out of date).

## The migrator

`@dafne/backend-migrator` applies the migrations of **every** database
package in **one order, by timestamp**, whatever their database. A fresh
server replays the history as it happened (e.g. `user` was created in
`dafne_sales`, later moved to `dafne_auth`).

- Each migration runs in its database (`USE`) and is recorded in that
  database's `_migrations`.
- Missing databases are created.
- One run at a time (`GET_LOCK('dafne_migrations')`).
- It needs **`MIGRATIONS_DATABASE_URL`**: the server URL with a user that
  can create and alter the `dafne_*` databases. Set it in the environment or
  in `packages/backend/migrator/.env`.

```sh
pnpm dafne db migrate                     # apply the pending migrations
pnpm dafne db generate                    # a migration of dafne_sales from the table changes
pnpm dafne db generate <package> --name x # of another database package
pnpm dafne db generate --custom --name x  # empty, for SQL written by hand
```

`generate` runs drizzle-kit, then fixes what drizzle-kit 1.0.0-rc.5 gets
wrong: it puts back `ON DELETE` / `ON UPDATE` dropped inside `CREATE TABLE`,
and adds the database name to foreign keys pointing to other databases.

In development, `dafne dev` runs `migrate:dev` before the APIs; it skips
with a warning when `MIGRATIONS_DATABASE_URL` isn't set.

## Migrations in production

Two options:

1. **The apps migrate on startup** with `MIGRATE_ON_START=true` (and
   `MIGRATIONS_DATABASE_URL`). `main.ts` calls `migrateOnStart` before Nest
   starts. Every app's build carries the migrations of **every** database
   (`dist/migrations/<database>/`), since they run in one order. Apps or
   replicas starting together are safe: one takes the lock, the others wait
   and find nothing to apply. A failing migration stops the app.
2. **A deploy step** runs `pnpm nx run @dafne/backend-migrator:migrate`
   before the apps are updated, and `MIGRATE_ON_START` stays off. Use this
   when the apps shouldn't hold a user with DDL rights.

Either way, a migration must keep working with the apps still running: add
first, drop in a later release.

## Grants

The apps' MySQL users (`DATABASE_URL`) need, besides their own database,
`SELECT` and `REFERENCES` on the tables of other databases they point to
(e.g. `dafne_auth.user`).

## Renaming `dafne_crm` to `dafne_sales`

The sales app was called CRM: its database was `dafne_crm` and its app key
in `app_access` was `crm`. In an environment created before the rename,
**before** deploying or running `pnpm dafne db migrate`:

```sh
pnpm dafne db move dafne_crm dafne_sales   # RENAME TABLE of every table, _migrations included
```

Then point the sales API's `DATABASE_URL` at `dafne_sales` (and give its
MySQL user the same grants there), set `DEFAULT_APPS=sales` in
`apps/auth`, and run `pnpm dafne db migrate`: the migration
`rename-crm-app-to-sales` of `dafne_auth` moves the users' access from `crm`
to `sales`.

## Moving the old `dafne` database

Environments created before the split have everything in `dafne`. Once:

```sh
pnpm dafne db move dafne dafne_sales   # RENAME TABLE of every table, _migrations included
```

Then point `DATABASE_URL` at `dafne_sales` and run `pnpm dafne db migrate`.
